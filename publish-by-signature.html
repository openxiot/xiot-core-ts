OIDC Trusted Publishing · openxiot/xiot-core-ts

信任，来自签名，不再来自令牌

我们把发布要求的“长期钥匙”换成了“一纸携带身份、几秒作废的签名”。于是 secrets 里的 NPM_TOKEN 删了，v0.2.0 照样发布成功。

✕ NPM_TOKEN 已删除 · 全链路无静态发布凭据

机制：一条签名链，五步走

没有共享密钥。npm 信任的不是口令，而是「GitHub 担保了此刻确实在 openxiot/xiot-core-ts 里跑 publish.yml」这份可验证的身份声明。

1

Runner 申请一份身份

workflow 里的 permissions.id-token: write，让构建服务器有权向 GitHub 的 OIDC 提供方申请一次性的身份令牌。

2

GitHub 盖上签名

OIDC 提供方签发一个 JSON Web Token（JWT），里面写着真实声明：仓库 openxiot/xiot-core-ts、工作流 publish.yml、ref refs/tags/v0.2.0。这份 JWT 用 GitHub 的私钥签名。

3

令牌跟着发布走

npm publish 把这份 id_token 当作本次请求的凭据，递交给 npm 注册表。

4

npm 验签，并对齐配置

npm 用 GitHub 的公开公钥（无需任何共享秘密）验证签名有效；再把声明与你登记的 trusted publisher 逐一比对——组织 openxiot、仓库 xiot-core-ts、工作流 publish.yml、环境留空。

5

一次性凭据，盖完章的产物

四格全对才放行：npm 给这次请求签发一个只有几分钟有效的短时凭据完成发布。产物自带一份 签名 JSON provenance（SLSA v1），可回溯到这台 workflow 与源码。

为什么删掉 NPM_TOKEN 反而能发

信任来源被整个换掉了：从「互相保管一个口令」变成「可验证的签名身份」。

维度旧 · NPM_TOKEN新 · OIDC
信任什么一个静态口令一份签名身份 + 你登记的发布方
凭据存哪打进仓库/组织 secrets，要保管不存，每次运行时临时签发
有效期长期（90 天得轮换）几分钟
泄露即风险面拿到就能冒充发版绑定仓库+workflow，转眼作废
本机依赖要有 token / 已登录无需任何本机凭据
对 CI 的意义一个需要保护的越权点身份本就属于你的 workflow，无从伪造

五道门，缺一不可

这些都就位，签名链才成立。你们的仓库刚好全满足（并以 v0.2.0 实测通过）。

  • workflow 声明 id-token: write

    让 runner 有权申请身份令牌。

  • npm ≥ 11.5.1

    Node 20/22 自带的都是 npm 10，需显式升级；别用 @latest（npm 12 默认关 allowScripts）。

  • 包 repository.url 与仓库精确一致

    npm 用它对上源码出处。

  • trusted publisher 四格精确

    工作流大写敏感写死 publish.yml；Environment 留空。

  • 勾选 “Allow npm publish”

    否则 OIDC 直发会 403，落入 staged 审批流程。

  • 没有残留 NODE_AUTH_TOKEN

    留一个空/旧 token 会让 npm 走令牌认证、直接 404，而不是回退 OIDC。

OIDC 到底是什么？ OIDC（OpenID Connect）是一套「让第三方确认「你是你」」的标准协议。这里 GitHub 是身份提供方（Issuer）——担保「正在跑的就是那个仓库里那个 workflow」；npm 是依赖方（Relying Party）——验证这份担保。两者不需预先共享密钥，因为 npm 用 GitHub 公开的签名公钥验签。这就是「没有令牌也能发」的根基。

几个词

OIDC

OpenID Connect，让依赖方验证身份的标准协议（身份提供方 / 依赖方 两方）。

id_token / JWT

签名后的身份令牌，内含仓库、工作流、ref 等声明，由 GitHub 私钥签发。

Issuer

身份提供方——此处是 GitHub，签发并签名身份声明。

Relying party

依赖方——此处是 npm，验签并决定是否放行。

Trusted publisher

你在 npm 后台登记的那四格，决定这份签名令牌能否代表该包发布。

Provenance

随包发布的签名构建记录，可回溯源码、工作流与构建环境。
